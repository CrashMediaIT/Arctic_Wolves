## Usage Guidelines

### For Developers

1. **Before Starting Work (MANDATORY)**
   - Review MAINTENANCE_PROCESS.md - understand complete workflow
   - Review STYLE_GUIDE.md - know UI standards
   - Check STRUCTURE.md - understand routing and dependencies
   - Reference DATABASE_SCHEMA_REFERENCE.md - verify table structures

2. **During Development**
   - Follow STYLE_GUIDE.md specifications exactly
   - Maintain STRUCTURE.md navigation patterns
   - Adhere to DATABASE_SCHEMA_REFERENCE.md conventions
   - Update ISSUES_TRACKER.md as you fix issues

3. **Before Committing**
   - Update STRUCTURE.md if files/routes/handlers changed
   - Update ISSUES_TRACKER.md with completed work
   - Create repair session summary if significant work done
   - Ensure all 4 governance documents remain synchronized

### For QA Team

1. **Testing Phase**
   - Use TESTING_CHECKLIST.md as primary guide
   - Reference NAVIGATION_MAP.md for coverage
   - Follow security testing in SECURITY_AUDIT.md
   - Verify against STYLE_GUIDE.md standards

2. **Bug Reporting**
   - Add new issues to ISSUES_TRACKER.md
   - Reference specific governance document sections
   - Include document version numbers
   - Link to relevant specifications

3. **Validation**
   - Verify completed issues match ISSUES_TRACKER.md status
   - Check STRUCTURE.md version history is current
   - Ensure governance documents synchronized

## Governance Synchronization

**Critical Principle**: All 4 core governance documents must remain synchronized.

When making changes:
1. Update the relevant primary document
2. Check if other governance documents need updates
3. Verify version numbers incremented appropriately
4. Confirm all cross-references remain accurate

**Documents that must stay in sync:**
- STRUCTURE.md ↔ ISSUES_TRACKER.md (routes, handlers, features)
- STYLE_GUIDE.md ↔ ISSUES_TRACKER.md (UI fixes)
- MAINTENANCE_PROCESS.md ↔ All others (governs all work)
